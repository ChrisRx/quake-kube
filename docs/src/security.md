# Security

What to know before making QuakeKube reachable by people you don't trust.

## The web app

By default the web app has no login. Anyone who reaches it can create up to
`gateway.maxServers` servers, and change or delete any server created there.
They can't touch servers created with `kubectl`, or set anything outside a
preset: the game, its content and its cvars come from `gateway.presets`, so
people only choose from what you've offered.

To limit this, do one or more of:

- Sign people in with a proxy (see [Authentication](authentication.md)).
- Turn off creating servers with `gateway.maxServers: 0`, which also removes the
  gateway's permission to create them.
- Keep the web app inside your network, which is what the chart does by default,
  with a ClusterIP Service.

Authentication only covers the web app. Native clients connect to game servers
directly, so use a server password or `gameServers.exposure.type: None` to keep
them out (see [Authentication](authentication.md#native-clients)).

## Passwords

A server's `game.password` is stored as plain text in its QuakeServer and its
Secret. Anyone who can read QuakeServers can read it, so it's for keeping
strangers off a server, rather than for anything sensitive. The web app only
sends a server's settings, including its password, to people who can manage it.

Each server's rcon password is generated by the controller and kept in its Secret
(see [Remote administration](setting-a-password.md#remote-administration)). Like
any Quake 3 rcon password, it crosses the network in the clear when a native client
uses it. The rcon password also authorizes sending a server a new configuration,
on port 8080 of its pod.

## What the gateway exposes

The gateway only forwards what browser clients need from a game server's pod: its
info, its content's manifest and pk3 files, and its maps' levelshots. A server's
`/metrics` and `/config` aren't reachable through it. Inside the cluster, pods can
reach port 8080 of game server pods directly, so use a NetworkPolicy if that
matters to you.

With `gateway.auth.mode: header`, the gateway trusts the headers it's given, so it
must only be reachable through the proxy.

## Permissions

The chart's roles:

| Who | Scope | Can |
|---|---|---|
| Controller | Cluster | Read QuakeServers and update their status, manage the Deployments, Services and Secrets of game servers, and read pods and nodes |
| Gateway | Cluster | Read QuakeServers, and ask the API server who's an admin when authentication is on |
| Gateway | `gateway.namespace` | Create, change and delete QuakeServers, read Secrets, run the pods that make map pictures, and keep their results in ConfigMaps |
| `<release>-admin` | Bound to `gateway.auth.admins` | Read and delete QuakeServers |

The gateway's Role can read every Secret in its namespace, since RBAC can't limit
it to the servers' Secrets. If the release namespace has other Secrets, give the
web app a namespace of its own with `gateway.namespace`. With `gateway.maxServers`
at 0, the gateway has no Role at all.

## What game servers run

Game server pods run ioquake3 and mods' QVMs, which the engine runs in a virtual
machine. The exception is `game.native`, which runs a mod's native library in the
server's process, with an executable stack (see
[Native game code](add-custom-maps.md#native-game-code)). The `rocket-arena-3`
preset uses it, so take that preset out of `gateway.presets` if you don't want to
offer it.

The controller and gateway run as non-root with read-only filesystems. Game
server pods don't set a security context.

A server's `content` can download from any URL, and `commands` and `cvars` go to
its console, so being able to create QuakeServers with `kubectl` means choosing
what the server runs.
